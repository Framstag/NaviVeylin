# Device evidence — fix-stale-zoom-walk-step (2026-10-13)

Verification of task 3.2: the fix's end-to-end behaviour on a device, against the same flow
that produced the defect report. Coordinate-free: magnifications, timestamps, pixel counts.

## Build under test

- `:app:assembleMobileDebug` from this change's tree, installed over the existing debug install on
  `emulator-5554` with `adb install -r -t` (x86_64, API 37). The app's map data survived the update
  (`run-as com.framstag.naviveylin ls files/maps` → `andorra`, unchanged).
- The reporting phone (Pixel 8, release `2026-10-11-1`) could not take the fix: a debug build does not
  match its release signature, and uninstalling to replace it would delete its maps and data. The
  comparison numbers below are therefore HEAD-on-the-phone against fixed-on-the-emulator, both measured
  with the same instrumented lines.

## How it was read

- logcat tags `MapCanvasVM`, `MapRenderer`, `TileCache` (`fitViewportToRoute`, `renderMap mag=`,
  `executeRender start`, `zoomWalk`); the app's own lines, no added instrumentation.
- route-paint pixels: `python3 .pi/logs/route-nav-start/count.py <png>`, calibrated on a frame known to
  carry the route (the overview frame) and on a frame without it (HEAD's parked frame).

## Scope of the claim

One paired measurement (precondition, fit, navigation start) on the emulator, plus the revert-check's
red/green pair on the host (`tasks.md` 3.1). Not measured: the phone itself with the fix installed, and
a moving vehicle (the follow re-render path). The off-road fix seen during the HEAD capture
(`Abseits der Straße`) is a property of the reporting phone's position, not of this change.
