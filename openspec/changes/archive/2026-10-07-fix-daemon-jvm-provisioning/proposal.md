# Proposal

## Why

The CI build has been red since 2026-10-06 and never reaches a task: Gradle cannot start its daemon.
`gradle/gradle-daemon-jvm.properties` (checked in) requires a **JetBrains** JDK 21 and carries ten
foojay package-id URLs; the runner installs only Temurin 21, so the vendor criterion cannot be
satisfied locally and Gradle falls through to provisioning — all ten URLs now answer `400 Bad
Request` ("Package id not found"). The failure is not caused by the commit that landed it
(`7922fe7`): the criteria file is unchanged since the initial import and the previous run
(`37121172567`, Oct 3) was green with it. Foojay's index currently serves no JDK 21 at all for
`temurin` or `jetbrains` on linux x64 (while `corretto` and `zulu` are intact), so the
upstream-recommended `./gradlew updateDaemonJvm` cannot be used right now either — and it would only
re-emit expiring ids (`gradle/foojay-toolchains#196`, closed NOT_PLANNED).

Workstations never see this: a local daemon already runs the auto-detected `/home/tim/.jdks/jbr-21.0.11`,
so the build never provisions. Only CI pays, at the cost of the whole job (~4-5 min of SDK, NDK and
vcpkg work before the failure) plus the gate evidence it owes the eighteen in-flight changes.

## What Changes

- **`gradle/gradle-daemon-jvm.properties`: drop the vendor criterion.** `toolchainVersion=21` stays;
  `toolchainVendor=JETBRAINS` goes. Any locally installed JDK 21 then satisfies the criteria — JBR 21
  on a workstation, Temurin 21 on the CI runner — so both start the daemon with no download and no
  third-party request.
- **Replace the ten foojay package-id URLs with durable vendor endpoints.** `toolchainUrl.<os>.<arch>`
  points at `https://api.adoptium.net/v3/binary/latest/21/ga/<os>/<arch>/jdk/hotspot/normal/eclipse`
  for linux, macOS and Windows on x64/aarch64. The `FREE_BSD` and `UNIX` entries are dropped: Adoptium
  has no such build, and a platform without a URL now reports "no defined toolchain download url"
  instead of a third party's 400. A machine with no JDK 21 at all still provisions — once.
- **`guidelines/Build.md`: document the JVM rule.** The build's daemon JVM requirement is a single
  version 21 with no vendor; provisioning URLs must be vendor-owned stable endpoints, never index
  package ids; and `updateDaemonJvm` must not be re-run to "refresh" the file — it rewrites expiring
  foojay ids.
- **`.github/workflows/build.yml`: correct the stale comment** that presents
  `-Dorg.gradle.java.home="$JAVA_HOME"` as the daemon-JVM override — daemon JVM criteria take
  precedence over it (`-Dorg.gradle.java.home`/`JAVA_HOME` remain in place for the native/vcpkg
  toolchain lookup, which reads `local.properties`). Hardening in the same step: add `~/.gradle/jdks`
  to the Gradle cache paths, so the one-time provisioning download is not repeated by every run if a
  future criteria change ever forces one.

Not changing: `settings.gradle.kts` keeps the `foojay-resolver-convention` plugin (it is what
generates the URLs) and no Gradle or AGP version moves.

## Capabilities

### New Capabilities

- `build-jvm-toolchain`: how the build declares and satisfies its JVM requirement — one vendor-neutral
  Java version, satisfied by the JDK already installed on the machine (CI runner or workstation), with
  a durable vendor endpoint as the fallback when none is installed.

### Modified Capabilities

None. No existing capability's requirements change: `build-test-gate` governs which suites a gate run
executes, `ci-vcpkg-cache` the vcpkg binary cache, `ci-unit-test-jni` the JNI stub and
`build-sbom` the SBOM — the JVM the daemon runs on is not covered by any of them.

## Impact

Affected files:

- `gradle/gradle-daemon-jvm.properties` — vendor criterion removed, ten URLs replaced (checked-in
  build config, generated by the `updateDaemonJvm` task).
- `.github/workflows/build.yml` — comment on the `Build debug APK` / `Set up JDK 21` steps, and the
  `Cache Gradle` path list.
- `guidelines/Build.md` — the new JVM rule.

Not affected: no Kotlin/Java/C++ source, no module in `:app`/`:auto`/`:core`/`:osmscout-client-java`,
no Android manifest or resource, no flavor, no native ABI, and no JNI bridge or libosmscout submodule
patch — this is not a native/JNI change. The produced APKs and AABs are byte-for-byte unaffected in
behavior: only the JVM that hosts the Gradle daemon changes on CI.

Kind: additive (build/CI tooling), no application behavior change. **Not breaking** for developers —
workstations keep starting the daemon on their existing JDK 21.

Rollback: revert the three files; the build then fails again exactly as it does today, so the
rollback costs nothing beyond the red CI it restores.

Guidelines referenced: `guidelines/Build.md` (build/test/release procedures, where the rule lands).
