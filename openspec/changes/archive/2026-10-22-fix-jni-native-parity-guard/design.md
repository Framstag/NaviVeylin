# Design — fix-jni-native-parity-guard

## Root cause

The JNI bridge has two Java sides and nothing compares them. `:osmscout-client-java` compiles the submodule's
`libosmscout-client-java/java` sources except five overridden files, so for those five the *only* Java copy the
APK sees is the override's — and a native declared on one side only is a `NoSuchMethodError` at the first call,
which no compiler and no test notices (`guidelines/Design.md` §5, issue #174). §119 fixed one instance of that
drift by hand and left the class unguarded.

One mechanism, not two. The trees are *correct* today: the divergence is intentional in both directions
(5 submodule-only, 5 override-only, measured — `evidence/surface.txt`). What is missing is the comparison, and
the reason it was never written is the item's own second half: a blanket "submodule natives ⊆ override natives"
check fails on the intended deviations, so it would have been a red build from its first run.

## The single fix

One rule, stated once and asserted twice:

1. **`buildSrc` — `com.naviveylin.build.jni.NativeParityScanner`** (pure, fixture-tested like the license, i18n,
   coordinate and transport scanners). For each of the five overridden files it computes the symmetric
   difference between the submodule's native declarations and the override's, as `name(type,type)` with package
   qualifiers stripped (`java.nio.ByteBuffer` → `ByteBuffer`, which is an import difference and not a
   divergence; `renderInto` is identical once that is done). The difference must equal the recorded list
   exactly, which makes both halves of the rule one comparison: an unrecorded divergence is a finding, and a
   recorded one the trees no longer carry is a finding too.
2. **`osmscout-client-java/native-parity.txt`** — the record: one line per divergence,
   `file | submodule-only|override-only | name(types) | reason`, ten lines today (five per direction), each
   reason naming the caller that needs the Android addition or the Android surface that made the submodule
   native unreachable. It is a *record of the trees*, not an allowlist: a stale line fails the gate, and a
   malformed line fails rather than silently dropping an allowance.
3. **`:app:checkNativeParity`**, wired into `preBuild` beside the eight existing gates, so the comparison runs
   in every `:app` build (CI's `:app:assembleMobileDebug`) and before a release. The scanner is the rule; the
   task only points it at the files and throws `GradleException(report)`.

## Alternatives the evidence eliminated

- **A blanket subset check (`submodule ⊆ override`)**: false on this tree — five submodule natives are absent
  from the override on purpose, and `startNavigation(long,NavigationListener)` is re-implemented there as a
  plain Java method delegating to `startNavigationWithVehicle(…, Vehicle.CAR, …)`. It would have failed from
  the first run and named nothing useful.
- **A mirror list of every native that must match**: a second copy of the submodule's 59 declarations, which
  then needs maintenance on every submodule bump and would drift exactly like the thing it guards. The
  symmetric difference is 10 lines and is generated by reading both trees.
- **Mirroring the missing natives instead of recording them**: not a guard, and the five submodule-only natives
  have no Android caller (`searchLocations(String,int,String,long)` has none in `:app`, `:auto` or `:core`; the
  Android search surface is admin-region-handle and structured-address based). Adding unused declarations to
  the override would grow the port's API to make a check pass, which is the opposite of the rule.
- **A host test only (no build gate)**: `:osmscout-client-java` is not exercised against the submodule's text
  by any test, and a unit test cannot see "the next submodule bump". The gate is what fails in the bump's own
  build.
- **The existing audit script instead of a new gate** (`.pi/skills/native-bridge-signature-change/scripts/bridge-signature-audit.sh`):
  it answers a different question — a Java declaration against the compiled `.so`'s symbols for one method,
  which proves the implementation matches the declaration, not that the override still mirrors the submodule's
  API. It cannot see a native the submodule declares and the override never had, which is the drift class this
  item is about; the two are complements, and the skill's Notes now name both.

## Blast radius

- `buildSrc/src/main/kotlin/com/naviveylin/build/jni/NativeParityScanner.kt` (new) and its five fixture cases.
- `app/src/test/java/com/naviveylin/build/NativeOverrideParityGuardTest.kt` (new, two cases).
- `osmscout-client-java/native-parity.txt` (new data file, ten lines plus a comment header).
- `app/build.gradle.kts`: one task registration plus one `preBuild` dependency.
- `guidelines/Design.md` §5 (the paragraph that lists the five overridden files), `guidelines/Build.md` §2
  (the configuration-cache measurement, now nine script-level tasks rather than eight).
- Capability delta: `osmscout-jni`, one requirement, seven scenarios.

No application source, no C++, no manifest, no dependency. `:osmscout-client-java`'s compiled API is unchanged:
the gate only reads files.

## Rollback

Revert the change's files. The gate is additive and inert without the scanner: removing the `checkNativeParity`
registration and the `preBuild` dependency restores the previous build exactly, and deleting
`osmscout-client-java/native-parity.txt` restores the previous tree — nothing else reads it.

## Risks and their mitigation

- **The gate fires while the submodule is not initialised** (fresh clone): the scanner reports the missing
  submodule directory as a finding with the `git submodule update --init` remedy, which is the same fail-closed
  choice `checkSubmoduleStylesheets` makes — and CI checks out submodules recursively. The task declares its
  inputs only when they exist, because `inputs.dir` on a missing path fails the task's *configuration* with
  `Input file does not exist` before the scanner can speak (measured on a throwaway project, 2026-10-22); with
  that guard the five findings are what a clone without the submodule prints
  (`evidence/missing-submodule-remedy.log`).
- **A false drift from formatting**: parameters are compared after comment stripping and package-qualifier
  stripping, so a re-wrapped declaration or a differently imported type is not a divergence; a *renamed*
  parameter is not one either (only its type is compared), which is the one normalization the pair needs.
- **The record becomes an allowlist**: both stale recordings and malformed lines fail, so it cannot outlive the
  trees it describes.
