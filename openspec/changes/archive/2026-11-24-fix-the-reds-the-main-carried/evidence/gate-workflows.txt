=== the mv guard
`run:` steps execute under `bash -e`, so an unguarded `mv` aborts the step — and the build — on a read-only or
full cache volume, against the step's own "a failed warm warns and lets the run continue" contract. Both steps
now guard the move and fall through to the same `::warning::` the download failure prints. The guard has no
local falsifier: no volume here refuses the move, so its evidence is the text in the diff, quoted above.

=== the mkdir guard (review round 4's NOTE N7)
The same contract covers the directory the jar is written into: `mkdir -p "$repo/$v"` stood unguarded between the
`-s` skip branch and the download, so a read-only or full cache volume aborted the step there — before the guarded
download and `mv` were reached. Both steps now guard it and `continue` to the next coordinate with the same
`::warning::`:

```
            if ! mkdir -p "$repo/$v"; then
              echo "::warning::could not create $repo/$v; the test-time fetch will ask Maven Central itself"
              continue
            fi
```

`build.yml` carries the full comment beside it; `sonar.yml` points at `build.yml`'s reason, as its `mv` guard
already does. Neither workflow's YAML changed shape: `yq -e .` on both exits 0, `tools/check-sonar-workflow.sh`
exits 0 and `tools/check-action-runtimes.sh` exits 0 after the edit. Like the `mv` guard, this one has no local
falsifier — no volume here refuses the `mkdir` — so its evidence is the text in the diff.
