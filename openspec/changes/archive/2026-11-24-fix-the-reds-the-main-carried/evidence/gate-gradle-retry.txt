## The named exclusion

The wrapper's *behaviour* is falsified offline by T1–T5. Its *effect* — that a throttled fetch no longer reddens
the run — is only observable in CI, so that sentence's evidence is the next green run of the workflow, not a
local case.

The wrapper ran and its window was exhausted — the run still failed. Read with

Three attempts, ~5 minutes, three 429s on the same coordinate. The wrapper did what it was built to do; the
throttle outlasted it.

**Why the throttle had something to throttle.** The step's own log shows the cache hit —
`Cache hit for gradle-Linux-m2-v1-707a6709…` — and the cache entry was created 2026-11-24T08:09:09Z, by the APK
job of run `45352034292` (`@272395a0`), which was **cancelled** at 08:26:09Z. Its size is 1 922 727 250 bytes,
against 2 755 978 060 for the pre-change entry — the partial save is smaller, and it lacks the
`nativeruntime-dist-compat` coordinates the unit-test classpath resolves. Every run since restored that partial
entry and re-downloaded what it lacks, which is what the throttle answered.

**The fix for the partial entry.** The entry was deleted — `gh cache delete 11019766323`, exit 0 — so the next
run's exact key misses and its `restore-keys: gradle-${{ runner.os }}-` fallback restores the pre-change entry
(2 755 978 060 bytes, complete). A successful run then saves a complete `m2-v1` entry. No workflow change: the
key's save-once rule means a complete entry is never overwritten by a partial one.

This is why the wrapper's window stays at 3 attempts: with a complete cache the step resolves nothing over the
network, so the wrapper is a backstop rather than the mechanism. A longer window would only wait longer on a
throttle that a complete cache never provokes.
