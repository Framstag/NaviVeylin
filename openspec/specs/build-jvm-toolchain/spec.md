# build-jvm-toolchain Specification

## Purpose
Defines how the build declares and satisfies the JVM its Gradle daemon runs on, so a workstation and a
CI runner resolve the same requirement from what each machine already has, and provisioning never
depends on a third party's rotating package ids — and holds the build's own scripts to the Gradle syntax
surface the next release keeps, and the project's own Kotlin sources to the one library spelling the
next Compose upgrade drops — the quadratic path builder — scanning no other library API, so an upgrade does
not fail on a construct this project can rewrite today.

## Requirements

### Requirement: The daemon JVM requirement names a version, not a vendor

The checked-in daemon JVM criteria SHALL require only a Java version (21). A machine that has any JDK 21
installed SHALL start the Gradle daemon on that installation without downloading a JDK.

#### Scenario: CI runner starts on the JDK the workflow installed

- **WHEN** a CI run has the JDK the workflow installs (Temurin 21) and no other vendor's JDK 21
- **THEN** the criteria are satisfied by that installation, the job reaches its first Gradle task, and the
  log contains no toolchain download attempt

#### Scenario: Workstation keeps the JVM it already uses

- **WHEN** a workstation's installed JDK 21 is of a different vendor than the machine on which the
  criteria file was generated
- **THEN** the criteria still match, the daemon starts on that installation, and no download occurs

#### Scenario: No routine run pays for a download

- **WHEN** either surface resolves the criteria from an installed JDK 21
- **THEN** the run provisions nothing, so the cost of the JDK is paid once at image/install time rather
  than per build

### Requirement: Provisioning URLs are durable vendor endpoints, not index package ids

Every per-platform URL in the checked-in daemon JVM criteria SHALL be a vendor-owned permanent endpoint
for the required version. No URL SHALL be a package-id redirect of a third-party JDK index, whose
records are pruned and whose ids then answer with an error.

#### Scenario: A pruned third-party record cannot break the build

- **WHEN** a third-party JDK index drops or renumbers the release its package id used to address
- **THEN** no checked-in URL addresses that index, and the build's toolchain resolution is unchanged

#### Scenario: Every declared platform resolves to its vendor archive

- **WHEN** each declared platform's URL is requested
- **THEN** it redirects to that vendor's archive of the required version, and the URL is one the vendor
  maintains rather than a record id

#### Scenario: A machine without the required JDK provisions once

- **WHEN** no JDK 21 is installed on a supported platform and that platform has a URL
- **THEN** the build downloads that version from the URL and starts the daemon, leaving the criteria
  file unchanged

#### Scenario: A platform without a vendor build says so itself

- **WHEN** a platform has no entry because the vendor publishes no build for it
- **THEN** the build reports the missing download URL for that platform instead of an error from a third
  party

### Requirement: The JVM rule and the regeneration caveat are checked in

The repository's build guidance SHALL state the daemon JVM version requirement, that the criteria are
vendor-neutral, and that regenerating the criteria file is a deliberate act: the Gradle task that writes
it re-emits third-party package-id URLs, which SHALL be replaced by durable vendor endpoints before the
file is committed.

#### Scenario: Rule survives a fresh clone

- **WHEN** a contributor clones the repository without local agent tooling
- **THEN** the JVM requirement and the regeneration caveat are readable in the checked-in build guidance

#### Scenario: A regenerated file is not committed as generated

- **WHEN** the criteria file is regenerated by the Gradle task that writes it
- **THEN** the regenerated package-id URLs are replaced with durable vendor endpoints under the same
  change, and the committed file names no index record id

### Requirement: The build's scripts use no construct Gradle 10 removes

The project's own Kotlin DSL build scripts SHALL register tasks by naming them — `tasks.register("name") { }` —
and SHALL use no `by registering`/`by getting`/`by creating`/`by existing` property delegate, which Gradle
9.6.1 deprecates on every configuration and Gradle 10 removes. A scan of every `*.gradle.kts` the project owns
SHALL report no such delegate, so a returning one is a failing case rather than a warning nobody reads.

#### Scenario: A project script registers its tasks by name

- **WHEN** a module script registers a check or an SBOM task
- **THEN** the registration names the task explicitly and the scan of the project's own `*.gradle.kts` files
  finds no delegate, while every task keeps the name its CI invocation already uses
- **Case**: `app: GradleScriptDeprecationTest` "no project build script uses a removed Gradle construct"

#### Scenario: The removal is still detectable

- **WHEN** the deprecated delegate form returns to a script, or a script names it only in a comment
- **THEN** the scan reports each offending line's number and text, and leaves the named form beside a comment
  alone — so a passing scan means the construct is absent, not that the scan cannot see it
- **Case**: `app: GradleScriptDeprecationTest` "the removal is still detectable"

### Requirement: The project's own Kotlin sources call no deprecated quadratic path builder

The project's own Kotlin sources SHALL build a quadratic Bézier by the name the pinned Compose ui release
keeps — `quadraticTo`/`relativeQuadraticTo` — and SHALL use no `quadraticBezierTo`/`relativeQuadraticBezierTo`,
which Compose ui 1.7.6 deprecates and a later release removes. A scan of every `*.kt` the project owns SHALL
report no such call, so a returning one is a failing case rather than one warning among the compile's others.

#### Scenario: A marker outline is built with the kept builder

- **WHEN** the location marker builds the path of its rounded tip
- **THEN** the scan of the project's own `*.kt` files reports zero deprecated quadratic spellings, and its
  printed measurement names the file count it read
- **Case**: `app: ComposeApiDeprecationTest` "no project Kotlin source calls a deprecated quadratic path builder"

#### Scenario: The scan is still detectable

- **WHEN** a source uses one of the deprecated spellings, or names one only in a comment
- **THEN** the scan reports a finding for that line, and leaves the kept spelling and a comment that names the
  deprecated one alone — so a passing scan means the spelling is absent, not that the scan cannot see it
- **Case**: `app: ComposeApiDeprecationTest` "the scan is still detectable"
