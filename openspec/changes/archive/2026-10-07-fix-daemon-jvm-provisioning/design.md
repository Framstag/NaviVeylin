# Design

## Context

See `proposal.md` — Why. The relevant current state:

- `gradle/gradle-daemon-jvm.properties` is checked in and was generated by the `updateDaemonJvm` task on
  a workstation whose JDK 21 is a JetBrains Runtime (`~/.jdks/jbr-21.0.11`). It therefore carries
  `toolchainVendor=JETBRAINS` plus ten `toolchainUrl.<os>.<arch>` entries that address **foojay Disco
  package ids**, e.g. `https://api.foojay.io/disco/v3.0/ids/0d1a1acdc708062093673f65aa9aba4b/redirect`.
- The URLs exist because `settings.gradle.kts` applies `org.gradle.toolchains.foojay-resolver-convention`
  1.0.0; that plugin is what the generator queries for a per-platform download URL.
- Per the Gradle 9.6.1 manual, daemon JVM criteria **take precedence over `JAVA_HOME` and
  `org.gradle.java.home`**. So `.github/workflows/build.yml`'s `-Dorg.gradle.java.home="$JAVA_HOME"`
  (and the `org.gradle.java.home` in `local.properties`, which `setup-vcpkg.sh` reads for its own JDK
  lookup) does not settle the daemon JVM.
- The runner installs Temurin 21 (`Set up JDK 21`). That is a JDK 21, but not a **JetBrains** JDK 21, so
  the vendor criterion excludes it. Gradle then provisions from the criteria URL and the request fails
  (`400 Bad Request`, "Package id not found").
- All ten ids currently answer 400, and foojay's index serves no JDK 21 for `temurin` or `jetbrains` on
  linux x64 at all (while `corretto` 25 and `zulu` 27 resolve), so the generator cannot produce a fresh
  file today. Upstream: `gradle/foojay-toolchains#196`, closed NOT_PLANNED ("regenerating one is a
  solution").
- The Gradle cache step caches `~/.gradle/caches` and `~/.gradle/wrapper/dists`, not `~/.gradle/jdks`
  (Gradle's provisioning target), so any provisioning repeats on every run.
- No repository guidance mentions the criteria file: neither `guidelines/Build.md`, `AGENTS.md` nor
  `README.md` names the daemon JVM, so nothing tells a maintainer not to regenerate it.

## Goals / Non-Goals

**Goals**

- Every surface resolves the daemon JVM from what it already has: the workstation's JBR 21, the runner's
  Temurin 21 — no network request on the routine path.
- Remove the dependency on a third party's rotating record ids from the checked-in file, so a prune
  upstream can never again stop the build at daemon start.
- Leave the version requirement (21) explicit and keep the file a valid criteria file: it must remain
  exactly what `updateDaemonJvm` writes, so the task can still be used deliberately.
- Make the rule checked in and CI-enforced, since the failure mode is invisible on any machine that
  happens to have the right JDK.

**Non-Goals**

- No change to Gradle, AGP, the Kotlin language level, `compileOptions`/JVM target, or the toolchain used
  to compile Kotlin/Java. This is the **daemon** JVM only.
- No change to the Android SDK/NDK/vcpkg environment, to any module, manifest, resource or flavor, and
  no native or JNI work.
- Not migrating the vcpkg or SBOM caches, and not re-litigating JDK 17 vs 21: 21 is what the file says
  today and what the runner installs.

## Decisions

### D1: Vendor-neutral criteria (drop `toolchainVendor=JETBRAINS`) — chosen

The criteria keep `toolchainVersion=21` and lose the vendor line. Gradle's manual: "If no vendor is
specified, Gradle considers all vendors compatible." Auto-detection then satisfies the criteria from the
JDK each machine already has.

*Alternatives*

- **Install JBR 21 in CI** (`actions/setup-java`, `distribution: jetbrains`, `java-version: 21`, which the
  action supports). Keeps workstation and runner identical and needs no edit to the criteria file, but:
  ~200 MB download per run unless the toolchain is cached by setup-java; and a workstation that has no
  JBR 21 (fresh clone on another machine) still hits the dead ids, because the file's provisioning URLs
  stay broken. It fixes CI while leaving the recurring class in place — rejected as the *only* measure,
  kept as the fallback if vendor-neutral matching turns out not to work on the runner (see Open
  Questions).
- **Vendor-pin Temurin** (`toolchainVendor=ADOPTIUM`). Matches the runner (no download) but *breaks the
  workstation*: the local JBR 21 no longer matches, so a local build would again try to provision from a
  dead URL. Rejected — it moves the failure rather than removing it.
- **Delete the criteria file.** Then the daemon JVM falls back to `org.gradle.java.home`, i.e. the
  committed machine-local path `/usr/lib/jvm/java-17-openjdk` on workstations and the `-D` override on
  CI: version drift per machine and no stated requirement. Rejected.

### D2: Durable vendor endpoints instead of foojay package ids — chosen

Each declared platform gets the vendor's permanent endpoint for the required version:
`https://api.adoptium.net/v3/binary/latest/21/ga/<os>/<arch>/jdk/hotspot/normal/eclipse` for linux
x64/aarch64, macOS x64/aarch64 and Windows x64/aarch64. Verified: each answers `307` to the vendor's
release archive (`github.com/adoptium/temurin21-binaries/releases/download/jdk-21.0.12.1+1/...`), and
`/latest/21/ga/...` always names the newest 21 GA, so the URL does not expire when a patch is released.
The `FREE_BSD` and `UNIX` entries are deleted: Adoptium publishes no such build, and Gradle's behaviour
without a URL is a first-party message ("No defined toolchain download url for ..."), which is a better
failure than a third party's 400.

*Alternatives*

- **Regenerate with the generator** (upstream's advice). Cannot run today (no JDK 21 left in the index to
  generate from) and re-emits the same expiring ids; the same breakage recurs at the next index prune.
  Rejected as the fix, but explicitly preserved as the deliberate path in the guidance — with the caveat
  that the generated URLs are replaced again before committing.
- **Drop provisioning entirely** (`toolchainPlatforms = []`). Simplest and fully offline, but a machine
  without a JDK 21 then fails with "no matching toolchain" and no remedy. Rejected: the endpoints cost
  nothing when a JDK 21 is installed, and they keep a fresh machine able to build.

### D3: Guard the criteria file in CI — chosen

A repository-hygiene check (same shape as the existing "Check libosmscout Android-free" and "Check
OpenSpec artifact hygiene" steps in `.github/workflows/build.yml`) fails the run when
`gradle/gradle-daemon-jvm.properties` contains an index package-id URL (`/disco/v3.0/ids/`) or lost its
`toolchainVersion=21` line. Cheap, and it turns the rule from a doc sentence into a gate that a
regenerated file cannot slip past.

*Alternatives*

- **Documentation only** — the rule in `guidelines/Build.md`, plus review. Rejected: the file is
  machine-generated, and the failure it causes is invisible on the workstation that regenerates it. The
  gate is five lines in a workflow that already carries two steps of this kind.
- **Detect it in Gradle** (a root verification task). More machinery for the same check, and a Gradle
  task cannot help a build that cannot start its daemon. Rejected: the gate must run before Gradle.

### D4: Cache the provisioning target too — chosen (hardening)

`~/.gradle/jdks` joins the Gradle cache paths. With D1+D2 the routine path never provisions, so this
only matters if a criteria change ever forces a download; then it pays once instead of once per run.
Included because the cache entry already exists and the path is one line.

*Alternative*: omit it — smaller cache, and the case is hypothetical. Accepted risk if the owner prefers
a minimal diff; it does not affect any requirement.

## Risks / Trade-offs

- [Gradle might not auto-detect the runner's Temurin 21 and still try to provision] → the endpoints are
  live, so provisioning would now succeed (and land in `~/.gradle/jdks`, cached per D4); the observable
  is the CI log line. Fallback is D1's JBR-in-CI path.
- [A vendor-neutral criterion lets a machine build with a different JVM than another] → the version is
  still pinned to 21, and nothing in this repository requires one vendor: no build script declares a
  toolchain vendor, and `kotlin.jvm.target=17` (language level) is independent of the daemon JVM.
- [Hand-editing a generated file makes a later `updateDaemonJvm` silently revert D2] → the guard in D3
  fails the CI run that carries such a regeneration, and the caveat is in `guidelines/Build.md`.
- [Adoptium's `latest/21/ga` moves within the same major] → intended: any 21 patch satisfies the
  criteria; the language level and the APK output do not depend on the patch number.
- [Removing the `FREE_BSD`/`UNIX` entries] → a build on those platforms must install a JDK 21 itself and
  gets a clear first-party error. No such platform builds this project today.

## Migration Plan

One commit, no data or state migration:

1. `gradle/gradle-daemon-jvm.properties`: drop `toolchainVendor=JETBRAINS`, replace the ten URLs with the
   six Adoptium endpoints, keep `toolchainVersion=21`, add a header comment stating that the file is
   generated but its URLs are maintained by hand and why.
2. `.github/workflows/build.yml`: add `~/.gradle/jdks` to the `Cache Gradle` paths; correct the
   daemon-JVM comment on the `Set up JDK 21` / `Build debug APK` steps.
3. New hygiene step checking the criteria file (D3).
4. `guidelines/Build.md`: the JVM rule, the generation caveat, and how to verify a change here.

Order matters: 1 before 3 (the guard would otherwise be born failing on the current file).

Rollback: revert 1–4. The build then fails again exactly as it does today, so rollback restores the
current (broken) CI rather than any lost work. Workstations are unaffected either way: the local daemon
keeps using `/home/tim/.jdks/jbr-21.0.11` under both the old and the new criteria.

## Verification

- **CI (primary)**: the next run passes the `Build debug APK` step and reaches `:app:assembleMobileDebug`;
  the log contains no "Unable to download toolchain" and no request to `api.foojay.io`.
- **Criteria guard (D3), revert-check**: reintroduce a `/disco/v3.0/ids/` URL, the hygiene step must fail;
  restore, it must pass. Without this mutation the guard is unproven.
- **URL check (D2)**: `curl -sS -o /dev/null -w '%{http_code}' -L --max-redirs 0 <url>` for each of the six
  endpoints returns `3xx`, and the redirect target is the vendor's 21 archive. No device or emulator is
  involved anywhere in this change.
- **No workstation regression**: `./gradlew --status` still reports the daemon for this project and
  `ps -o args= -p <pid>` still shows `/home/tim/.jdks/jbr-21.0.11/bin/java`.
- **No unit test is owed**: the change touches no Kotlin/Java code. The guard's mutation step above is the
  falsification the change owes; a host JVM test cannot read daemon criteria meaningfully, since a test
  runs *after* the daemon has started from exactly those criteria.

## Open Questions

- Whether Gradle's auto-detection on the runner picks up the setup-java Temurin 21 (via `JAVA_HOME`) when
  the criteria carry no vendor, or still provisions. Not decidable locally — every local check has a JBR 21
  to match. The next CI run answers it; the answer does not change the specs or the task order, only
  whether D1's fallback is ever needed.
