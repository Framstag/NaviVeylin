## What was NOT renamed

No rule name changed, none was added, none removed. §9 still carries its seven named rules and §10 its one,
under the same numbers in a different document — which is why a stale reference is repairable by naming a
different file and never by renumbering.

## What the duplicate rule would catch

`check-doc-routes.sh` reports a rule name stated twice **within one document** and **across
`guidelines/*.md`**. A cut that copied a section instead of moving it, or that left a rule in both halves,
fails there rather than passing silently — the reason `--sizes` alone is not the cut's proof.

## One thing this change did not fix, and the review then did

`tools/doc-routes.json` carried two `"UI.md §7"` *section* entries that `guideline-uiphone-cut` left behind;
`UI.md` has carried no §7 since that cut moved it to `UIPhoneMap.md` §7. No check reads section names in this
map — only glob existence and rule reach — so it was invisible to CI.

This change recorded it and handed it to its owning change. The independent review of the four cuts marked it
blocking, and the owning change is in the set and still open, so the correction round **deleted both entries**.
Doing that exposed what they had been hiding: the map's reached-set contains a line per entry, and those two
junk lines padded it. With them gone, `check-rule-routes.sh` reported one genuinely unreached rule,
`guidelines/DesignNative.md` §5b "the map scan publishes only what this build can read", whose own line was
malformed (`**Rule: X** **X.**`). Both are repaired — the line reads `**Rule: X** The map scan …` and the map
names it under `DesignNative.md §5b`.
